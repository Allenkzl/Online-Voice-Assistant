# GLM-4-Voice Phase 0 实测记录（2026-09-10）

> 用 `scripts/glm_voice_poc.py` 真调智谱 GLM-4-Voice，回答"这条路能不能走"的关键问题。
> 测试音频：项目 `tests/asr_*.wav`（macOS `say` 合成，16 kHz 单声道）+ 实验室的英文噪声/空域样本。
> 环境：本机（Apple Silicon）→ 公网 → `open.bigmodel.cn`；每次一个独立请求，非流式。

---

## 1. 结论速览

| 问题 | 实测答案 |
|---|---|
| 接口形态 | ✅ 一次 Chat-Completions 调用即可（音频进 / 音频出），**不需要 WebSocket** |
| 输出音频格式 | ⚠️ 裸 PCM **24 kHz / 单声道 / 16 bit**（官方示例写的 44100 是错的，见 §6.1 的纠正记录） |
| 请求延迟 | ✅ **1.1~1.9 s**（按正确的 24k 渲染，回复约 3~7 秒音频）；近似 `0.6 + 0.25×音频秒数` |
| 端到端总延迟（推算，CM4） | **约 2.5~3 s**（VAD 1.2s + 请求 1.2~1.7s + 转码/aplay），优于现在的 3~8 s |
| 成本 | ✅ ¥0.014~0.021/轮（173~268 tokens @ ¥80/百万） |
| 回复长度可控性 | ⚠️ 人设必须显式限制，否则一次回复 5~11 秒音频（见 §3） |
| **中文发音** | ✅ **清晰可懂**（本地 ASR 回听近乎逐字） |
| **英文发音** | ❌ **可懂度差**——两句纯英文被两个独立 ASR 都判为不可懂（见 §4） |
| 语言跟随 | ⚠️ **不可靠**：人设提到"英文"就会连中文问句也答英文；完全不提英文时英文输入又答中文（见 §5.1） |
| 密钥/额度 | 账号需为 GLM-4-Voice 单独充值或买资源包（`code 1113`）；`glm-4-flash` 有免费额度可用来先验证 key |

| 输入 | 输出音频 | 请求耗时 | tokens | 成本 |

| 中英混说（未收紧人设） | 11.07s | 4.00s | 455 | ¥0.0364 |

## 4. 英文发音问题（本次最重要的发现）

把返回音频用**两个独立 ASR** 回听（本地 SenseVoice 中英模型 + Whisper-base 强制英文）：

| 模型说的英文 | SenseVoice 回听 | Whisper 回听 | 判定 |
|---|---|---|---|
| "Welcome to the smart retail area!" | `我 the什么呀。`（语种判成 zh） | `Welcome to the SMAPYCALL-E!` | ❌ 关键词完全不可懂 |
| "Of course, I understand English sentences! How can I assist you today?" | `Of course I English how do I.` | `I press R on each door and close the door…` | ❌ 不可懂 |
| "Welcome to the Smart Retail Zone! Here, you can explore innovative零售技术 and solutions." | `Welcome to the smart retail zone. here. you can explore any of video technologies and solutions.` | `Welcome to the Slight Reconphone! …` | ⚠️ 部分可懂（开场句可懂，专名不可懂） |

**对照中文**（同一批测试，同一套回听方式）：

| 模型说的中文 | SenseVoice 回听 | 判定 |
|---|---|---|
| "智慧零售区，欢迎参观！" | `智慧零售区欢迎他们。` | ✅ 基本逐字 |
| "这里是充满关怀的主动关怀区域。" | `这里是充满关怀的主动关怀。` | ✅ 几乎逐字 |

**说明**：ASR 回听只是客观代理指标，人耳对带口音的英文容忍度更高——**务必自己听一遍**：

```bash
open /tmp/glm_voice_poc_short2      # 收紧人设后的中英样本
open /tmp/glm_voice_poc_en          # 纯英文问答样本
```

**影响与建议**：
- 中文访客：GLM-4-Voice 可用（延迟与清晰度都够）。
- 英文访客：建议仍走 **pipeline 引擎**（qwen3-tts 的英文），或后续评估千问 Omni / GLM-Realtime 的英文表现。
- 需要做一次 **A/B 客观对比**：同一句英文分别用 `qwen3-tts-flash` 和 GLM-4-Voice 合成，用同一套 ASR 回听打分（需要机器人上的 `DASHSCOPE_API_KEY`）。

| 输入语言 | 回复语言 | 是否符合预期 |
|---|---|---|
| 中文 | 中文 | ✅ |
| 英文（smart retail） | 英文 | ✅ |

## 5.1 人设措辞与语言跟随（追加实验，重要）

对同一句中文输入（"智慧零售区，欢迎参观。"）做 A/B，每次 1 次调用：

| 人设写法 | 中文输入的实际回复 | 结论 |
|---|---|---|
| 包含"英文不超过12个单词" | `Welcome to the smart零售区!` | ❌ 被带成英文 |
| 包含"用户讲英文时你只能讲英文" | `Welcome to the smart零售区!` | ❌ 同样被带成英文 |
| **完全不提英文**，只写"语言跟随用户" | `欢迎来到智慧零售区！体验最新的科技与购物结合的乐趣吧！` | ✅ 中文 |
| 同上但限"最多15个字" | `智慧零售区，欢迎光临！体验现代科技与购物相结合的乐趣吧！` | ✅ 中文 |

**关键发现：人设里只要出现"英文"相关约束，模型就会倾向用英文回答（连中文问句也是）。**
反过来，完全不提英文时，英文输入又常常得到中文回复：

| 人设 | 英文输入 "Welcome to the Smart Retail area." |
|---|---|
| 不提英文（现用） | `欢迎来到智能零售展区！需要我为您介绍什么吗？`（中文，❌ 未跟随） |

→ **GLM-4-Voice 的语言控制不可靠，没有一种措辞能两个方向都对。**
展厅以中文访客为主，因此**默认人设选择"不提英文"的中文优先版本**（写入
`DEFAULT_PERSONA`）。若以后要严格跟随语种，可行方案是加一个**轻量语种识别（LID）**，
按识别结果在每轮人设里追加"用英文回答"（比跑完整 ASR 快得多，约 100ms 级）。

## 6. 音频格式与转换链路（已验证）

```
GLM 返回 message.audio.data (base64)
   → 解码得裸 PCM 44.1k/单声道/16bit（无 WAV 头）
   → device_wav_bytes(): scipy resample_poly 44.1k→16k（160/441）+ repeat 成双声道
   → 16 kHz / 2ch / 16bit WAV（与线上 aplay 要求一致）
```

回听校验证据：中文回复经上述链路后，本地 ASR 几乎逐字还原 → **采样率假设与重采样实现都正确**。
`glm_voice_pcm_rate` 可配置，出现变调时可改（听感判断）。

## 6.1 音色与响度：为什么"听起来像机器人"（线上实测后追加）

线上首测后反馈"音频有点像机器人的声音"。逐项排查结果：**不是转码错误，是音色与响度差异**。

### ⚠️ 采样率：**第一版结论是错的，正确值是 24000**（线上实测纠正）

**踩坑记录（重要）**：官方示例里写的是 `setframerate(44100)`，我据此把默认采样率设为 44100，
并用"让模型重复我的话、比较时长"来验证——输入 2.56s，44.1k 假设下输出 2.20s（0.86x，"语速一致"），
于是**错误地判定 44100 正确**。

这个推理的漏洞：**它假设模型复述时会保持输入语速**，而实际不是。真机上线后现场反馈
"像机器说的叽里咕噜、听不清楚"，用**音节速率**才看清真相：

| 假设采样率 | 同一句回复的时长 | 语速（汉字音节/秒） | 判定 |
|---|---|---|---|
| 44100（错） | 3.63 s | **6.6 音节/秒** | ❌ 远快于正常（4~6 才正常）→ 又急又尖、听不清 |
| **24000（对）** | 6.68 s | **3.3 音节/秒** | ✅ 正常对话语速 |

**两条独立证据**：
1. **人耳 A/B**：同一段 PCM 按 44.1k / 32k / 24k 三档渲染后盲听，现场判定"24k 那版才像正常中文"。
2. **频谱带边**：按 44.1k 解释时，18–22 kHz 仍有 -24 dB 能量——真实频率即 9.8–12 kHz，
   正是 24 kHz 编解码器的带限；真正的 44.1k 录音不会在这一段有可感能量。

**结论**：`DEFAULT_PCM_RATE = 24000`，可用 `glm_voice_pcm_rate` / `WAKE_GLM_VOICE_PCM_RATE` 覆盖。
**方法论教训：用"时长/音节速率"当判据，别用"复述时长对比"；最终必须人耳确认。**

**同句 A/B（"智慧零售区，欢迎参观！"）**：

| | 时长 | 响度 RMS | 95%能量上限 | 谐噪峰值 |
|---|---|---|---|---|
| 千问 TTS（qwen3-tts-flash / Cherry） | 2.32s | **0.086** | 1222 Hz | 0.51 |
| GLM-4-Voice 原始输出 | 2.12s | **0.046** | 1975 Hz | 0.43 |

→ GLM 的输出**低约 5.5 dB、高频占比更高**（发薄、发尖），谐噪比也更低，听感就是"又轻又尖"，
容易被描述成"机器人声"。

**进一步定位（第二轮）**：单纯提音量只能加 1.13x，因为 GLM 输出**峰均比高达 22dB**。查峰值位置发现：

| 位置 | 值 |
|---|---|
| 第 0 个采样点（响度） | **0.35 ~ 0.71**（直流跳变/爆音） |
| 去掉首尾 50ms 后峰值 | 0.41 |
| 语音主体 RMS | 0.041 ~ 0.054 |

即：**每条回复开头都有一个爆音**，它既听起来是机械"咔"声，又把响度限制器卡在低增益上。

**最终处理链**（`audio.normalize_loudness()`，日志 `E2E_LEVEL`）：

```
裸 PCM → 去直流 + 首尾 8ms 淡入淡出（消爆音）
       → 一极前馈压缩器（threshold 0.15 / ratio 4 / attack 5ms / release 80ms，压峰值）
       → 响度对齐到 target_rms=0.09
       → 峰值上限 0.97（不削波）
       → 44.1k→16k 重采样 → 双声道 WAV
```

实测效果（同一句"智慧零售区，欢迎参观！"）：

| | RMS | 峰值 | 首样本 |
|---|---|---|---|
| 千问 TTS | 0.080 | 0.45 | -0.000 |
| GLM 原始 | 0.041 | 0.66 | **+0.350**（爆音） |
| GLM 处理后 | **0.090** | 0.65 | +0.006 |

可用 `glm_voice_target_rms` / `WAKE_GLM_VOICE_TARGET_RMS` 调整目标响度。
**音色本身**（相对千问 TTS 更"合成/发尖"）无法靠后处理消除，需人耳最终判定。

## 7. 复现命令

```bash
export ZHIPUAI_API_KEY=<智谱 key>

# 三语言基线（默认人设）
python3 scripts/glm_voice_poc.py tests/asr_en_smart_retail.wav \
        tests/asr_zh_smart_retail.wav tests/asr_mixed_smart_retail.wav

# 指定人设 + 单独输出目录
python3 scripts/glm_voice_poc.py tests/asr_mixed_smart_retail.wav \
        --persona "回答只用一句话：中文不超过25个字，英文不超过12个单词。" \
        --out-dir /tmp/poc --log /tmp/poc.jsonl
```

结果同时写入 JSONL（默认 `/tmp/glm_voice_poc.jsonl`），便于多次对比。
